# wxAutoControl 架构说明初稿

> 本初稿由扫描项目结构与源码生成，重点基于当前仓库中的 Python 实现归纳，建议结合实际业务背景、运行环境和后续需求说明继续补充。

## 1. 项目定位

`wxAutoControl` 是一个面向 Windows 桌面微信客户端的自动化控制项目，当前目标比较聚焦，主要提供两类能力：

- 向指定会话发送消息
- 通过手机号发起添加好友申请

项目没有沿用旧的 mmui 业务控件树作为唯一依赖，而是同时兼容以下两种识别思路：

- 优先通过 `uiautomation` 定位微信顶层窗口与内容窗口
- 当业务控件树不可用时，退回到基于截图、OCR、相对坐标和键鼠事件的“视觉自动化链路”

从当前代码看，这个仓库更像一个独立可执行的自动化能力包，而不是完整业务系统。外部系统只需要调用 `wxautocontrol.add_friend.add_friend` 或 `wxautocontrol.send_message.send_message` 即可触发自动化动作。

## 2. 技术栈与运行依赖

项目主体使用 Python 编写，核心依赖集中在以下几类：

- Windows UI 与系统交互：`pywin32`、`uiautomation`
- 图像与 OCR：`Pillow`、`opencv-python`、`numpy`、`rapidocr_onnxruntime`
- 剪贴板与进程能力：`pyperclip`、`psutil`
- 日志输出：标准库 `logging` + `colorama`

项目显然假定运行环境为 Windows 桌面，并且依赖一个已经启动、可见、可交互的微信客户端窗口。自动化执行依赖前台窗口、鼠标点击、剪贴板写入和截图能力，因此不属于后台无界面任务。

## 3. 目录与模块划分

当前仓库结构比较集中，主要分成 4 个层次。

### 3.1 `wxautocontrol/`

这是核心业务包，负责对外暴露 API、组织控制流程，以及封装视觉自动化细节。

- `__init__.py`
  对外导出 `WeixinController`、`ControlConfig`、`ControlResponse`
- `api.py`
  聚合导出 `add_friend` 与 `send_message`
- `client.py`
  控制器主入口，负责串联窗口检测、节流控制、发送消息流程、添加好友流程
- `visual.py`
  项目最核心的视觉自动化模块，负责截图、OCR、坐标缓存、点击、输入、窗口查找、添加好友页面与申请弹窗操作
- `add_friend.py`
  添加好友能力的轻量封装入口
- `send_message.py`
  发送消息能力的轻量封装入口
- `state.py`
  暴露添加好友节流状态
- `exceptions.py`
  UI 相关异常定义
- `common/`
  通用底层能力，如日志、锁、窗口检测、Win32 工具、公共类型

### 3.2 `tests/`

这里不是单元测试目录，而是两个命令行脚本入口，用于人工或半自动运行能力验证。

- `run_add_friend.py`
- `run_send_message.py`

这两个脚本负责解析命令行参数、设置日志开关、打印输入参数，并调用业务包中的公开函数。

### 3.3 `wxauto_logs/`

运行日志目录。`common/log.py` 会按日期写入日志文件，例如 `app_YYYYMMDD.log`。

### 3.4 `.Knowledge/` 与 `.task/`

这部分属于 Flow2Spec 和运行时配套目录，不是业务运行核心，但对文档和缓存有辅助作用。

- `.Knowledge/`
  存放知识库、架构说明、路由配置等
- `.task/runtime/visual-weixin-cache.json`
  当前视觉自动化链路的坐标缓存文件

## 4. 对外入口与调用路径

项目对外入口很薄，主要有两层。

### 4.1 包级入口

- `wxautocontrol.add_friend.add_friend(...)`
- `wxautocontrol.send_message.send_message(...)`

这两个函数都会初始化 `WeixinController`，然后调用控制器中的具体方法。

### 4.2 脚本入口

通过 `tests/` 下脚本可以直接从命令行触发：

```bash
python tests/run_add_friend.py --phone 13800000000
python tests/run_send_message.py --who 张三 --msg "你好"
```

其中添加好友脚本已经支持 `--entry-mode` 参数，用于区分不同入口模式：

- `global_search`：从微信主窗口的全局搜索进入
- `add_menu`：点击搜索框旁边的加号菜单，再进入“添加朋友”

这说明当前项目既在提供能力，也在沉淀“可复现的操作脚本”作为调试入口。

## 5. 核心控制流程

### 5.1 控制器层：`WeixinController`

`client.py` 中的 `WeixinController` 是业务编排中心，承担以下职责：

- 根据昵称尝试定位目标微信窗口
- 对外暴露 `send_msg` 与 `add_new_friend`
- 使用 `uilock` 保证 UI 操作串行执行
- 在添加好友前做时间节流，避免过快重复操作
- 将底层视觉操作结果转换为统一的 `ControlResponse`

从架构上看，控制器层是“业务流程编排器”，而不是底层驱动本身。它不负责复杂的 OCR 细节，而是把这些工作委托给 `visual.py` 中的窗口对象。

### 5.2 发送消息流程

发送消息的路径相对简单：

1. 创建 `WeixinController`
2. 检测微信主窗口是否存在
3. 构造 `VisualWeixinWindow`
4. 调用 `send_message_to_session(...)`
5. 根据结果组装 `ControlResponse`

虽然当前扫描中没有完整展开 `send_message_to_session` 的内部细节，但从结构上可以确认：发送消息与添加好友共用同一套视觉窗口基类和窗口检测能力。

### 5.3 添加好友流程

添加好友是当前仓库里最复杂的流程，控制路径如下：

1. 校验手机号和 `entry_mode`
2. 根据全局状态做添加好友频率控制
3. 创建主窗口视觉对象
4. 按入口模式进入“添加朋友”流程
5. 定位 `VisualAddFriendWindow`
6. 判断搜索结果状态
7. 打开“申请添加好友”弹窗
8. 填写验证信息、备注、标签、朋友权限
9. 点击确认提交
10. 再根据页面状态推断结果，并返回标准响应

当前添加好友流程已经体现出几个明确设计点：

- 入口模式可配置，不把 UI 入口写死
- 搜索、按钮点击、页面状态识别都做了 OCR 与缓存结合
- 对“未找到用户”“已是好友”“频率受限”“权限限制”等状态做了显式区分
- 节流状态通过全局锁与时间戳管理

## 6. 视觉自动化链路

`visual.py` 是整个项目最关键的实现层，也是系统复杂度的主要来源。

### 6.1 基础能力

`VisualWeixinWindow` 作为基础类，提供一组通用视觉驱动能力：

- 读取窗口矩形和尺寸
- 将相对坐标转换为屏幕绝对坐标
- 激活窗口、调整窗口大小
- 截图并保存
- 调用 RapidOCR 识别文本
- 在 OCR 结果中匹配目标文本框
- 鼠标点击、键盘输入、回车、ESC、方向键等基础动作

这意味着业务层不直接与 Win32 API 打交道，而是通过窗口对象抽象执行操作。

### 6.2 坐标缓存机制

视觉链路中已经实现了坐标缓存，缓存文件位于：

` .task/runtime/visual-weixin-cache.json `

缓存机制的设计意图很明确：

- 优先复用历史成功点击点，减少 OCR 次数
- 缓存既保存当前窗口尺寸下的绝对点，也保存共享的比例坐标
- 当缓存点超出预期区域或点击后无法推进到下一状态时，会清理缓存并回退到 OCR

从实现上看，这套缓存不是单纯“命中即用”，而是“缓存优先、失败再 OCR 纠偏”的策略，更适合桌面 UI 这种位置大致稳定但偶尔偏移的场景。

### 6.3 多窗口角色

`visual.py` 中并不只有一个窗口类，而是围绕不同界面拆成了多个角色：

- `VisualWeixinWindow`
  微信主窗口与公共操作基础类
- `VisualAddFriendWindow`
  “添加朋友/资料页”窗口
- `VisualAddFriendSearchWindow`
  从菜单模式进入后的手机号搜索窗口
- `VisualAddMenuPopup`
  主窗口右上角加号弹出菜单
- `VisualFriendRequestWindow`
  “申请添加好友”表单弹窗
- `VisualSearchPopup`
  搜索相关弹层

这种拆法说明作者把每个窗口当作单独的状态节点处理，而不是在一个大类里硬编码所有分支。整体上属于“窗口对象 + 状态识别 + 动作封装”的结构。

### 6.4 OCR 与启发式混合定位

项目没有完全依赖 OCR 文本框中心点，而是大量使用混合策略：

- OCR 识别文本作为强特征
- 基于窗口比例的启发式坐标作为兜底
- 限定区域边界校验缓存点是否合法
- 必要时对文本框进行扩展，点击更可靠的行区域

这说明当前方案的目标不是理论上的 UI 结构完美识别，而是追求“在真实微信客户端上更高的可操作成功率”。

## 7. 窗口检测与兼容策略

`common/window.py` 负责定位微信窗口。它会先尝试常见类名：

- `mmui::MainWindow`
- `WeChatMainWndForPC`

如果无法直接拿到业务内容树，再尝试根据顶层窗口名如“微信”或 “WeChat” 检测候选，并向下查找：

- `mmui::MainWindow`
- `WeChatMainWndForPC`
- `Chrome_WidgetWin_0`

最终会给出一个 `WindowDiagnostic`，区分不同客户端形态：

- `mmui`
- `qt-webview-host`
- `qt-shell-only`
- `unknown`

这层能力的意义在于：项目并不假设微信客户端只有一种固定实现，而是先判断当前运行形态，再决定是否走视觉链路。

## 8. 并发、状态与响应模型

### 8.1 UI 串行化

`common/lock.py` 中的 `uilock` 基于进程锁、线程锁和异步锁三层包装，确保同一时刻只有一个 UI 自动化动作在执行。对桌面自动化来说，这个约束是必要的，否则多个流程会争抢前台窗口、鼠标和剪贴板。

### 8.2 全局状态

当前全局状态比较少，主要集中在添加好友节流：

- `_last_add_friend_ts`
- `_add_friend_state_lock`

这说明现阶段项目不是复杂状态机，而是用极少量全局状态控制一个高风险操作的调用频率。

### 8.3 统一返回结构

所有对外调用都通过 `ControlResponse` 返回，统一包含：

- `status`
- `message`
- `data`

这使得脚本层或后续接入方不需要解析底层异常，直接根据结构化结果做判断即可。

## 9. 配置与运行特征

当前运行配置集中在 `common/types.py` 中的 `ControlConfig`：

- `ENABLE_FILE_LOGGER`
- `ADD_FRIEND_TIMEOUT`
- `ADD_FRIEND_INTERVAL`
- `FIXED_MAIN_WINDOW_WIDTH`
- `FIXED_MAIN_WINDOW_HEIGHT`

这些配置都以类常量方式存在，说明当前项目暂时没有引入独立配置文件或环境变量体系。对于一个单机桌面自动化工具来说，这种方式足够直接，但后续如果需要多环境运行或对外发布，可能需要更灵活的配置加载机制。

## 10. 日志与可观测性

日志能力由 `common/log.py` 提供，具备以下特点：

- 控制台彩色输出
- 首次写日志时自动创建文件日志
- 日志默认按天滚动到 `wxauto_logs/`
- 调试模式可以通过脚本参数打开

从当前实现看，视觉自动化链路中写了比较多 `debug` 日志，尤其是定位来源、缓存命中、OCR 结果和提交后状态判断。这对排查桌面自动化问题非常关键，因为很多失败都不是代码异常，而是“页面状态与预期不一致”。

## 11. 当前架构特点总结

从这次扫描结果看，项目整体有以下几个比较鲜明的架构特点：

- 能力边界清晰，当前只围绕“发消息”和“加好友”两条链路展开
- 业务编排和视觉驱动基本分层，控制器不直接承担底层 OCR 细节
- 面向真实桌面 UI 波动做了缓存、启发式坐标和 OCR 的混合设计
- 提供脚本化入口，方便本地验证和问题复现
- 仍偏向单机工具形态，配置、状态和运行入口都比较轻量
